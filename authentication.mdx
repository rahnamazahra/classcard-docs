## Section 1: Business & Product Overview

### Why our authentication is different

Most class-management platforms give every organization on the platform the same login screen and trust a single shared database to keep tenants apart. We don't. Every request in this system is resolved to **one specific organization's isolated schema before a single row of user data is touched**.

<CardGroup cols={2}>
  <Card title="5 Login Methods" icon="key">
    Password, Phone OTP, Student ID + PIN, Magic Link, and SSO — chosen per user type.
  </Card>
  <Card title="Schema-Isolated Tenants" icon="database">
    Users, sessions, and credentials live in physically separate schemas. No shared table leakage.
  </Card>
  <Card title="JWT + Server Sessions" icon="shield-check">
    Short-lived signed tokens backed by revocable database sessions for instant logout control.
  </Card>
  <Card title="Audit Trail" icon="file-shield">
    Every login, failure, and credential change is recorded in a hash-chained audit log.
  </Card>
</CardGroup>

### Supported login methods

| Method | Who it's for | What's required |
| :--- | :--- | :--- |
| **Email + Password** | Staff, administrators, organization owners | Registered email + password |
| **Phone OTP** | Guardians and students without email habits | Registered phone number (6-digit code) |
| **Student ID + PIN** | Young students, front-desk assisted login | Student ID + 4+ digit PIN |
| **Magic Link** | Low-frequency portal users | Registered email (24h one-time link) |
| **SSO (Single Sign-On)** | Enterprise staff (Google, Entra ID, Okta) | Provider account linked to organization |

<Note>
  A **session** is what every method above produces: a database-backed session plus a signed token pair. This allows instant server-side revocation during password resets or suspicious activity.
</Note>

### How each method works

<AccordionGroup>
  <Accordion title="1. Email + Password">
    <Steps>
      <Step title="User submits credentials">
        User submits email and password via login interface.
      </Step>
      <Step title="System verifies account">
        Account is looked up inside tenant schema and password hash is checked.
      </Step>
      <Step title="Session and tokens issued">
        System creates a tracked session, returning access token (1 hour) & refresh token (30 days).
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="2. Phone OTP">
    <Steps>
      <Step title="Request Code">
        User submits registered phone number.
      </Step>
      <Step title="Code Generation">
        A 6-digit code valid for 10 minutes is generated and dispatched.
      </Step>
      <Step title="Verify & Login">
        User submits code; platform issues session upon successful verification.
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="3. Student ID + PIN">
    <Steps>
      <Step title="Input Credentials">
        Student enters unique Student ID (e.g., `STU-ACME-001`) and PIN.
      </Step>
      <Step title="Verification">
        System checks Student ID and PIN pairing within tenant context.
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="4. Magic Link">
    <Steps>
      <Step title="Request Link">
        User requests sign-in link via email.
      </Step>
      <Step title="Single-Use Token">
        A signed link valid for 24 hours is sent to the inbox.
      </Step>
    </Steps>
  </Accordion>

  <Accordion title="5. SSO (Single Sign-On)">
    <Steps>
      <Step title="Link Identity">
        User links account with Google, Microsoft, or Okta in profile settings.
      </Step>
      <Step title="Provider Authentication">
        Subsequent logins authenticate through provider identity handshake.
      </Step>
    </Steps>
  </Accordion>
</AccordionGroup>

## Section 2: Technical Architecture & Implementation

### Design patterns

| Pattern | Location | Purpose |
| :--- | :--- | :--- |
| **Action Classes** | `Actions/*Action.php` | Single-use-case classes with `execute()` method for clean testability. |
| **Thin Repositories** | `Repositories/UserLookupRepository.php` | Reserved for non-trivial query shapes. |
| **DTOs** | `DataTransferObjects/*.php` | Strongly typed `final readonly` classes across boundary layers. |
| **Domain Exceptions** | `Exceptions/*Exception.php` | Centralized error rendering with clear HTTP status mapping. |

### Multi-tenancy execution pipeline

<Steps>
  <Step title="Tenant Resolution">
    `TenantMiddleware` extracts subdomain (e.g., `acme.classcard.app`) and identifies Organization.
  </Step>
  <Step title="Schema Switch">
    `TenantContext::setOrganization()` repoints DB connection to tenant's schema.
  </Step>
  <Step title="Tenant-Scoped Models">
    Models use `TenantScoped` trait to enforce context presence before executing queries.
  </Step>
  <Step title="Context Cleanup">
    `TenantMiddleware::terminate()` resets DB connection back to central landlord state.
  </Step>
</Steps>

### API Endpoint Reference

| Method | Endpoint | Auth Required | Rate Limit |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/login` | No | `login` (5/min) |
| `POST` | `/api/login/otp/request` | No | `login` (5/min) |
| `POST` | `/api/login/otp/verify` | No | `login` (5/min) |
| `POST` | `/api/token/refresh` | No (Uses Refresh Token) | `login` (5/min) |
| `POST` | `/api/logout` | Yes (`auth:api`) | `api` (60/min) |
| `GET` | `/api/me/linked-students` | Yes (`auth:api`) | `api` (60/min) |
